## 문서 맵

| 파일 | 역할 | 알 수 있는 것 |

## 읽는 순서

```
00-overview  →  01-product  →  02-specs  →  03-design  →  04-tasks  →  05-conventions
   (지도)         (무엇을)        (어떻게)      (어떻게 보이나)   (지금 뭐 하나)    (어떻게 쓰나)
```

새 태스크를 시작하기 전 이 순서대로 읽는다.
파일이 존재하지 않으면 작업을 진행하기 전에 사용자에게 확인한다.

---

## 왜 이렇게 나누는가 — 관심사 분리(Separation of Concerns)

하나의 문서에 모든 내용을 담으면 다음 문제가 생긴다.

- **변경 충돌**: 기능 정의가 바뀔 때 기술 명세·컨벤션까지 같은 파일을 수정해야 한다.
- **맥락 오염**: "무엇을 만드나"와 "어떻게 만드나"가 섞이면 의사결정 근거가 흐려진다.
- **탐색 비용**: 필요한 정보를 찾기 위해 전체 문서를 읽어야 한다.

각 파일은 **단 하나의 질문에만 답한다.**

| 질문 | 담당 파일 |
|------|----------|
| 이 제품은 누구를 위해 무엇을 하는가? | `01-product.md` |
| 기술적으로 어떻게 구현되는가? | `02-specs.md` |
| 화면과 흐름은 어떻게 생겼는가? | `03-design.md` |
| 지금 무엇을 만들고 있는가? | `04-tasks.md` |
| 코드와 협업은 어떤 규칙을 따르는가? | `05-conventions.md` |

이 분리 덕분에 한 관심사가 변해도 다른 파일은 영향받지 않는다.
기능 범위가 바뀌면 `01-product.md`만, 기술 스택이 바뀌면 `02-specs.md`만 수정한다.
